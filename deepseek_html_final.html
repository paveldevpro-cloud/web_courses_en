Streaming in LangGraph: modes, CLI, FastAPI, SSE

LangGraph · Ollama · FastAPI · Pydantic 4 lessons + advanced · ~55 minutes Intermediate level

A four-lesson section plus an advanced SSE lesson. Lessons 1–2 cover the three streaming modes and the console stream. Lessons 3–4 wrap the app in FastAPI + Pydantic: base routes, a JSON /ask endpoint, and an /index endpoint with an optional URL. The advanced lesson adds SSE streaming for the browser.

Section overview

LangGraph can stream at three levels, and beginners often get confused about which mode to pick. That's why we split this topic into four lessons plus an advanced one. In the first lesson you'll see all three modes on the same graph — the difference is exactly one line of code. In the second we apply the right mode to our RAG agent and get a live token stream in the terminal. In the third we wrap the app in FastAPI and Pydantic: base routes, request and response schemas, and a run example. In the fourth we add an optional URL parameter to the indexing route so the same endpoint can re-index a different page. And in the advanced lesson we add SSE streaming — the transport that lets a browser consume tokens in real time.

Lesson 1

Three streaming modes: values, updates, messages

Goal: run astream with three different stream_mode values on the same graph and see what each one returns.

0. Lesson intro 0:00–1:00

Slide with the three modes and the tagline: "one graph, one line — three different behaviors".

In this lesson we're not going to apply anything. The goal is to understand the tool. LangGraph has three streaming modes, and the choice between them determines what you see in the stream. We'll take our existing RAG graph and run it three times — with values, updates, and messages. The code difference is exactly one line.

1. Setup: enable streaming=True 1:00–2:00

Open main.py, find the ChatOpenAI constructor, add streaming=True.

llm = ChatOpenAI(
    model=os.getenv("CHAT_MODEL", "llama3.1"),
    base_url=os.getenv("LLM_API_BASE", "http://127.0.0.1:11434/v1"),
    api_key=os.getenv("LLM_API_KEY", "ollama"),
    temperature=0,
    streaming=True,  # the LLM streams tokens
)
One line — streaming=True. It's needed for all three modes, but it's critical for messages: without it LangChain won't ask Ollama to stream tokens, and the messages mode won't produce a gradual stream.

2. Mode values 2:00–5:00

stream_mode="values"

Create a file inspect_stream.py. Import the existing graph and run astream with the values mode.

# inspect_stream.py
import asyncio
from main import rag_graph

MODE = "values"

async def inspect(question: str):
    print(f"\n=== stream_mode = {MODE} ===\n")
    async for chunk in rag_graph.astream(
        {"question": question, "context": "", "sources": [], "answer": ""},
        stream_mode=MODE,
    ):
        print(chunk)
        print("-" * 60)

if __name__ == "__main__":
    asyncio.run(inspect("What is the promo code?"))
The values mode returns the full graph state after each node. Watch: first the empty state, then retrieve fills in context and sources, then generate fills in answer. This is handy for debugging: you can see how data flows through the whole graph.

3. Mode updates 5:00–8:00

stream_mode="updates"

Change one line: MODE = "updates". Run again.

{'retrieve': {'context': 'The promo code is ...', 'sources': ['https://...']}}
------------------------------------------------------------
{'generate': {'answer': 'The promo code is SMART2024'}}
------------------------------------------------------------
The updates mode returns only what a node changed. The key is the node name, the value is its return. Watch: retrieve returned context and sources, generate returned answer. This is handy for logs and for collecting sources in parallel with the token stream.

4. Mode messages 8:00–11:00

stream_mode="messages"

Change the line to MODE = "messages". The chunk structure is different here — it's a (message_chunk, metadata) tuple.

MODE = "messages"

async for message_chunk, metadata in rag_graph.astream(
    {"question": question, "context": "", "sources": [], "answer": ""},
    stream_mode=MODE,
):
    print(repr(message_chunk.content), "| node =", metadata.get("langgraph_node"))
'The' | node = generate
' promo' | node = generate
' code' | node = generate
Here it is — the mode this whole section is about. messages returns LLM tokens as they are generated. Note: the chunk is a tuple of two elements, message_chunk and metadata. The metadata contains the langgraph_node key — the name of the node that produced this token.

Lesson 2

Adding streaming output to a RAG agent

Goal: turn the synchronous ask_question into an asynchronous ask_question_stream and see tokens in the terminal.

0. Lesson intro 0:00–0:40

In the previous lesson we learned that the messages mode returns tokens and node metadata. Now let's apply it to our RAG agent. We'll make three changes: enable streaming=True on the model, write an async wrapper with astream, and switch the entry point.

1 Enable token streaming on the LLM 0:40–2:30

llm = ChatOpenAI(
    model=os.getenv("CHAT_MODEL", "llama3.1"),
    base_url=os.getenv("LLM_API_BASE", "http://127.0.0.1:11434/v1"),
    api_key=os.getenv("LLM_API_KEY", "ollama"),
    temperature=0,
    streaming=True,  # the LLM streams tokens
)
If you skipped lesson 1 — here's the only thing you need from it for this lesson: streaming=True in the ChatOpenAI constructor. Without it, stream_mode="messages" won't give you a gradual stream.

2 Write the async wrapper with astream 2:30–7:00

async def ask_question_stream(question: str) -> None:
    print("\nAnswer:")

    async for message_chunk, metadata in rag_graph.astream(
        {
            "question": question,
            "context": "",
            "sources": [],
            "answer": "",
        },
        stream_mode="messages",
    ):
        if (
            message_chunk.content
            and metadata.get("langgraph_node") == "generate"
        ):
            print(message_chunk.content, end="", flush=True)

    print()
The function is async — astream returns an async generator. Inside the async for loop we get a pair: the message chunk and the metadata. The langgraph_node key in the metadata tells us which node produced this chunk. We filter by generate. Then we print the content: end="" glues tokens into one line, flush=True makes them appear immediately.

3 Switch the entry point to the stream 7:00–8:30

if question:
    asyncio.run(ask_question_stream(question))
ask_question_stream is an async function, so we launch it via asyncio.run. You can keep the old synchronous ask_question in the file.

4. Run and observe the result 8:30–9:30

Ask a question (or 'exit'): What is the promo code?

Answer:
The promo code for the advanced course is SMART2024...
There's the stream. Tokens appear as they are generated. Subjectively the answer arrives faster, even though the total time is the same — the user simply sees progress.

5. Bonus: Sources during streaming 9:30–10:30

In the messages mode, sources don't come through — only tokens. There are two approaches. The first is to call retrieve again after the stream: cheap, but duplicates the search. The second is to listen to stream_mode=["messages", "updates"] in parallel and collect sources from updates. For the educational example we'll stick with the first.

6. Summary and homework 12:00–12:45

  • streaming=True in the ChatOpenAI constructor
  • async def ask_question_stream(...) with astream(..., stream_mode="messages")
  • asyncio.run(ask_question_stream(...)) in __main__
  • we understand that this is a local console stream, not a network protocol
Homework: add timing to ask_question_stream — measure time to the first token and to the last one. You'll see that streaming doesn't speed up generation, but it radically improves perceived performance. Next lesson — wrapping the app in FastAPI and Pydantic.
Lesson 3

FastAPI + Pydantic wrapper

Goal: wrap the RAG app in a FastAPI service with typed request/response schemas via Pydantic, base routes (/health, /ask, /index), and a run example. SSE streaming is a separate advanced lesson.

0. Lesson intro 0:00–0:30

Slide: on the left — the CLI app from lesson 2, on the right — a running web service with /health, /ask, and /index routes.

So far our app runs in the terminal. That's fine for learning, but not for a real product. In this lesson we'll wrap the app in FastAPI and add Pydantic schemas for request and response. We'll get a running web service with three base routes: a health check, an ask endpoint that returns the full answer as JSON, and an index endpoint that triggers index_documents. This is the foundation. In the advanced lesson we'll add SSE on top of it so the ask endpoint can stream tokens to a browser.

1. Install FastAPI 0:30–2:00

Before we start

If you haven't installed FastAPI yet, run the following command in your terminal:

pip install "fastapi[standard]"
If you haven't installed FastAPI yet, do it now by running pip install "fastapi[standard]" in your terminal. The [standard] extra pulls in uvicorn — the ASGI server we'll use to run the app — and a few other goodies. If you're using uv, the equivalent is uv add "fastapi[standard]". Pydantic ships with FastAPI, so you don't need a separate install.

2. Pydantic schemas for request and response 2:00–5:00

Create a new file schemas.py next to main.py. Define four models: AskRequest, AskResponse, IndexResponse, and HealthResponse.

# schemas.py
from pydantic import BaseModel, Field


class AskRequest(BaseModel):
    question: str = Field(
        ...,
        min_length=1,
        max_length=2000,
        description="The user's question for the RAG agent",
        examples=["What is the promo code?"],
    )


class AskResponse(BaseModel):
    answer: str = Field(..., description="The generated answer")
    sources: list[str] = Field(
        default_factory=list,
        description="Source URLs used to generate the answer",
    )


class IndexResponse(BaseModel):
    indexed: int = Field(..., description="Number of chunks indexed")
    source: str = Field(..., description="The URL that was indexed")


class HealthResponse(BaseModel):
    status: str = "ok"
Pydantic models describe the shape of the data going in and out. AskRequest has a single field question with validation: it can't be empty and can't exceed 2000 characters. AskResponse has answer and sources. IndexResponse tells the client how many chunks were indexed and from which URL. HealthResponse is for the health check route. These schemas do three things: validate incoming data, document the API automatically, and give you type hints in the editor.

3. FastAPI app with base routes 5:00–8:00

Create server.py. Import the graph, index_documents, and the schemas, wire up three routes: /health, /ask, and /index.

# server.py
from fastapi import FastAPI

from main import rag_graph, index_documents, SOURCE_URL
from schemas import (
    AskRequest,
    AskResponse,
    IndexResponse,
    HealthResponse,
)

app = FastAPI(
    title="RAG Agent API",
    version="1.0.0",
    description="A simple RAG agent exposed over HTTP.",
)


@app.get("/health", response_model=HealthResponse)
async def health() -> HealthResponse:
    return HealthResponse(status="ok")


@app.post("/ask", response_model=AskResponse)
async def ask(payload: AskRequest) -> AskResponse:
    result = rag_graph.invoke(
        {
            "question": payload.question,
            "context": "",
            "sources": [],
            "answer": "",
        }
    )
    return AskResponse(
        answer=result["answer"],
        sources=result["sources"],
    )


@app.post("/index", response_model=IndexResponse)
async def index() -> IndexResponse:
    index_documents()
    return IndexResponse(
        indexed=vector_store._collection.count(),
        source=SOURCE_URL,
    )
Three routes, three responsibilities. /health returns a tiny JSON — useful for load balancers and monitoring. /ask takes AskRequest, runs the graph synchronously with invoke, and returns AskResponse. /index calls index_documents() — the same function you ran from the CLI with main.py index — and returns how many chunks are in the vector store and which URL was indexed. Notice that the response_model argument tells FastAPI to validate and serialize the output, and it also makes the schema appear in the auto-generated docs.

Why invoke and not astream here?

  • This lesson is about the FastAPI wrapper, not about streaming.
  • invoke returns a complete answer as JSON — easy to test and reason about.
  • Streaming over HTTP is a separate topic with its own protocol (SSE). It's covered in the advanced lesson.

4. The /index route in detail 8:00–10:00

Zoom in on the /index route. Show the call to index_documents() and explain that it re-runs the whole pipeline: fetch, split, embed, store.

The /index route is a thin wrapper around index_documents from main.py. When you call it, the server fetches the page from SOURCE_URL, splits it into chunks, generates embeddings, and writes them to ChromaDB. Depending on the page size this can take a few seconds — so the response comes back when indexing is complete, not immediately. In the next lesson we'll make the URL a parameter so the same route can index a different page without changing the code.

Idempotency note

  • index_documents uses content-based hashes as document IDs, so re-indexing the same page doesn't create duplicates.
  • If the page changed, new chunks get new IDs and old ones stay in the store. A production system would also need a cleanup step — we'll mention it as homework.

Lesson 4

Optional URL for indexing

Goal: extend the /index route so the client can pass a custom URL. When no URL is provided, the route falls back to SOURCE_URL from the environment.

0. Lesson intro 0:00–1:00

Slide: the /index route with two call examples — one with no body, one with {"url": "https://example.com"}.

In the previous lesson /index always used SOURCE_URL from the environment. That works for a single-site app, but in a real RAG service you often want to index a different page without redeploying. In this short lesson we'll make the URL an optional parameter: pass a body with a url field to index that page, or send no body to fall back to SOURCE_URL.

1. Extend the schema 1:00–3:00

Open schemas.py. Add an optional IndexRequest model. Update IndexResponse to include the URL that was indexed.

# schemas.py — add IndexRequest, keep IndexResponse as is
from pydantic import BaseModel, Field, HttpUrl


class IndexRequest(BaseModel):
    url: HttpUrl | None = Field(
        default=None,
        description="Optional URL to index. If omitted, SOURCE_URL is used.",
        examples=["https://aismartcode.vercel.app/"],
    )
Two things to notice. First, the field is optional: url: HttpUrl | None = None. If the client sends an empty body or no body at all, the route will use SOURCE_URL. Second, we use HttpUrl instead of plain str — Pydantic will validate that the input is a proper HTTP or HTTPS URL and reject anything else with a 422. That saves us a manual URL check in the route.

2. Update the route to accept the URL 3:00–6:00

Open server.py. Change index_documents in main.py to accept an optional URL, then update the /index route.

Step A. In main.py, make index_documents accept an optional URL:

# main.py
def index_documents(url: str | None = None) -> int:
    target = url or SOURCE_URL
    documents = load_data(target)
    chunks = split_documents(documents)

    ids = [
        hashlib.sha256(
            f"{chunk.metadata['source']}:{i}:{chunk.page_content}".encode()
        ).hexdigest()
        for i, chunk in enumerate(chunks)
    ]

    vector_store.add_documents(documents=chunks, ids=ids)
    print(f"Indexed {len(chunks)} chunks from {target}")
    return len(chunks)

Step B. In server.py, accept an optional IndexRequest body:

# server.py
@app.post("/index", response_model=IndexResponse)
async def index(payload: IndexRequest | None = None) -> IndexResponse:
    url = str(payload.url) if payload and payload.url else SOURCE_URL
    count = index_documents(url=url)
    return IndexResponse(indexed=count, source=url)
Step A is in main.py: index_documents now takes an optional url argument. If it's None, we fall back to SOURCE_URL. It also returns the number of chunks so the route can report it. Step B is in server.py: the route accepts an optional IndexRequest body. If the body is missing or url is None, we use SOURCE_URL. FastAPI treats the parameter as optional because it has a default of None, so a request with no body still works.

Why HttpUrl and not str?

  • Pydantic validates the scheme (http or https) and the host.
  • Invalid URLs are rejected with a 422 before they reach load_data.
  • The generated docs show the field as a URL input, not a free-form string.

3. Test both cases 6:00–8:00

Case 1: no body — index the default SOURCE_URL.

curl -X POST http://127.0.0.1:8000/index
# {"indexed": 42, "source": "https://aismartcode.vercel.app/"}

Case 2: custom URL — index a different page.

  -H "Content-Type: application/json" \

# {"indexed": 17, "source": "https://example.com/"}

Case 3: invalid URL — Pydantic rejects it.

curl -X POST http://127.0.0.1:8000/index \

Three cases, three behaviors. No body — the route falls back to SOURCE_URL. Custom URL — the route indexes that page and reports the normalized URL in the response. Invalid URL — Pydantic rejects it before any indexing happens, with a clear 422. This is exactly the kind of small, safe extension Pydantic is designed for: you add a field, and validation and docs come for free.

Advanced lesson

SSE streaming: pushing tokens to the browser Advanced

Goal: add a /stream endpoint that sends tokens to the browser as they are generated, using the Server-Sent Events protocol. Understand what SSE is, why it fits LLM streaming, and how to test it with curl and a minimal EventSource client.

0. Lesson intro 0:00–1:00

Slide: on the left — the /ask endpoint returning one big JSON, on the right — a browser receiving tokens one by one. An arrow between them: "same data, different transport".

In lesson 3 we built /ask — it returns the full answer as one JSON. That works, but the user still waits for the whole generation before seeing anything. In lesson 2 we already had a token stream in the terminal. Now let's expose it over HTTP so a browser can consume it. That's what SSE is for: Server-Sent Events, a protocol that lets a server push data to a client over a single HTTP connection.

1. What is SSE 1:00–3:30

Slide: a diagram — "client → HTTP request → server → one-way event stream → client".

SSE is a mechanism that lets a server push data to a client over a single HTTP connection. Unlike WebSocket, where both directions are open, SSE is one-way: the server sends, the client only reads. That's exactly what LLM streaming needs: the user sent a question, the server is generating the answer and sending tokens as they become available. At that moment the client has nothing to send back.

Show what an SSE stream looks like in the browser DevTools: lines like data: {"token": "The"}, data: {"token": " promo"}, and so on.

Technically SSE is a regular HTTP response with the Content-Type: text/event-stream header. The server doesn't close the connection; instead it gradually writes lines in a special format: data: ... followed by two newlines at the end of each message. The browser's EventSource reads this stream and fires a handler for each message. If the connection drops, the browser automatically reconnects after a few seconds.

2. Why SSE, not WebSocket 3:30–5:30

A comparison slide of the three transports.

JSON /ask (lesson 3)SSEWebSocket
TransportHTTP request/responseHTTP streamingseparate protocol
Clientfetch / curlbrowser / EventSourcebrowser / WebSocket
Directionone request, one responseserver → clientboth ways
Time to first tokenafter full generationimmediateimmediate
Complexityminimalmediumhigh
Why not WebSocket? Because WebSocket is needed when both sides send data over the same connection — for example, a voice chat where the microphone and the speaker work simultaneously. For text chat with an LLM, the client sent a question and is waiting. There's nothing to send back. SSE is a standard, simple, and sufficient tool. It works over regular HTTP, doesn't require a separate protocol, and is supported by every browser through EventSource. And why not just keep /ask as JSON? Because the user waits for the full generation. SSE gives the first token almost immediately, which is the whole point of streaming.

3. Add the /stream endpoint 5:30–9:00

Open server.py. Add a new route /stream next to /ask. Import StreamingResponse and json.

# server.py — add these imports at the top
import json
from fastapi.responses import StreamingResponse

Then add the route below /ask:

@app.get("/stream")
async def stream(question: str):
    async def event_generator():
        async for message_chunk, metadata in rag_graph.astream(
            {"question": question, "context": "", "sources": [], "answer": ""},
            stream_mode="messages",
        ):
            if (
                message_chunk.content
                and metadata.get("langgraph_node") == "generate"
            ):
                payload = json.dumps({"token": message_chunk.content})
                yield f"data: {payload}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",  # disable nginx buffering
        },
    )
Watch the shape. The body of event_generator is almost a copy of our ask_question_stream from lesson 2 — same astream, same stream_mode="messages", same langgraph_node == "generate" filter. The difference is that instead of print we yield a string in SSE format. Each token is packed into data: {"token": "..."}\n\n — the two newlines are mandatory, they're the frame separator. At the end we send data: [DONE]\n\n so the client knows the stream is over. The X-Accel-Buffering: no header is needed if nginx sits in front of FastAPI: without it nginx buffers tokens and delivers them in batches instead of one by one.

Why GET and a query parameter?

  • EventSource only supports GET — no request body.
  • So the question travels as a query parameter: /stream?question=....
  • If you need a body, use fetch with a streaming reader instead of EventSource.

Show a minimal HTML file with EventSource. You don't have to type it — just show and explain.

<!DOCTYPE html>
<html>
<body>
  <div id="answer"></div>
  <script>
    const q = encodeURIComponent("What is the promo code?");
    const source = new EventSource(`http://127.0.0.1:8000/stream?question=${q}`);

    source.onmessage = (event) => {
      if (event.data === "[DONE]") {
        source.close();
        return;
      }
      const data = JSON.parse(event.data);
      document.getElementById("answer").textContent += data.token;
    };
  </script>
</body>
</html>
The client creates an EventSource and points it at the endpoint URL. Every message triggers onmessage. We check whether it's [DONE], parse the JSON, and append the token to textContent. That's it. The browser keeps the connection open and reconnects on its own if something drops. That's the main advantage of SSE: minimal client code, no libraries. Open this file in a browser with the server running and you'll see tokens appear in the page as they're generated.
