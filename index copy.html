Block 2. Rag pipeline logic

Narration

Before we write code, let’s get the logic. RAG means Retrieval-Augmented Generation. It works in two phases. Indexing and Answering questions. For Indexing: take a document, split it into chunks, turn them into vectors, and put them in a store. To Answera question, find the most similar chunks and give them to the model as context.

Every RAG system starts with data. We’ll download a page, remove the noise — scripts, styles, navigation, and footer — and keep only clean text. The rule I follow is simple: get rid of unnecessary content to reduce hallucinations. The cleaner the data, the more accurate the search.

Block 3. Indexing and getting data from URL

Narration

Let's start with the indexing phase. We need to get data from the URL and split it into chunks. Create a load_data function that will do this for us.

  • First of all, we need to get data from the URL that we passed as an argument, using the requests library.
  • Then we need to parse the HTML content using the BeautifulSoup library.
  • Now we need to remove the noise from the content using the following tags: script, style, nav, footer. Because these tags are not needed for the content and they will only add garbage to the content.
  • Also, let's add validation to the function: if the content is not found, we will raise an error.
  • And the final step — where the magic happens — is to return the chunks as a list of Document objects. For this purpose, we will use the Document class from the LangChain library.
python 
def load_data(url: str) -> list[Document]:
    response = requests.get(
        url,
        timeout=20,
        headers={"User-Agent": "RAG-Tutorial/1.0"},
    )
    response.raise_for_status()

    soup = BeautifulSoup(response.text, "html.parser")

    for tag in soup(["script", "style", "nav", "footer"]):
        tag.decompose()

    text = soup.get_text(separator=" ", strip=True)

    if not text:
        raise ValueError("No text content found at the URL")

    return [Document(page_content=text, metadata={"source": url})]

Block 6. Split data into chunks

Narration

Why not just give the model the whole page? First, models have a limited context window. Second, search over a huge text gets fuzzy. So we split a large document into chunks — small meaning-sized pieces.

when we got our data from the URL, we need to split it into chunks.

python 
# 2. Split data into chunks
def split_documents(documents: list[Document]) -> list[Document]:
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=800,
        chunk_overlap=150,
    )
    return splitter.split_documents(documents)

In the code, we use RecursiveCharacterTextSplitter class from LangChain library. It will split the text into chunks of 800 characters with 150 characters overlap. Why did we choose numbers of characters? Because it is a good balance between the context window of the model and the accuracy of the search. The overlap is important to avoid losing context when the chunks are joined together. You can experiment with different values to find the best one for your model.

Block 7. Vector store and prompt

Narration

when we finished with the splitting, we need to store the chunks in a vector store. We will use Chroma class from LangChain library. It will store the chunks in a vector store. lets create vector store.

python 
vector_store = Chroma(
    collection_name="rag_documents",  # collection name, like a table name in a regular database.
    embedding_function=embeddings,  # tell the store which model to use for vectors
    persist_directory=DB_PATH,  # persist_directory points to the location on the disk.
)

A vector store holds text chunks together with their vectors and can instantly find the nearest ones. embedding_function tell the store which model to use for vectors, both when adding and when searching. It must be the same model, or the "maps of meaning" won't line up. And persist_directory points to the location on the disk where the data will be stored. if the directory does not exist, it will be created.

Block 8. Steps 3–4 — embeddings and save to Chroma

Narration

When we create the vector store, we need to add the chunks to it. Now let's put the indexing process together using the functions we've created to load, split, embed, and store the data. Let's create an index_documents function. We'll load the data from source_url using the load_data function, then split the loaded document into chunks using the split_documents function.

python 
# 3–4. Generate embeddings and store chunks in ChromaDB
def index_documents() -> None:
    documents = load_data(SOURCE_URL)
    chunks = split_documents(documents)

    # identifiers for each chunk, to avoid duplicates in case of a second run.
    ids = [
        hashlib.sha256(
            f"{chunk.metadata['source']}:{i}:{chunk.page_content}".encode()
        ).hexdigest()
        for i, chunk in enumerate(chunks)
    ]

    vector_store.add_documents(documents=chunks, ids=ids)  # add the chunks to the vector store.

    print(f"Indexed {len(chunks)} chunks from {SOURCE_URL}")

Then we'll build the list of identifiers for each chunk using unique ID based on a hash, to avoid duplicates in case of a second run. And finally we will use add_documents method from Chroma class to add the chunks to the vector store. And print information about the number of chunks that were added.

Block 9. Graph state

Narration

Now one of the most interesting parts. LangGraph describes a process as a graph: nodes are steps, edges are transitions between them. To save the state between the nodes, we will use a dictionary,that every node reads and updates. You can consider it like a memory. We will use TypedDict class from typing module to define the schema of the state.

python 
# 5–9. RAG workflow

The state schema is the definition of the keys that will be used in the state dictionary. We will use the following keys:

  • the user's question
  • the joined text of retrieved chunks
  • the list of sources
  • and the final answer

Block 10. Nodes and the retrieval step

Narration

Now lets create our nodes.retrieve function will create the retrieval node. It performs semantic search to retrieve the most relevant chunks based on vector similarity.

python 
# 6–7. Retrieve relevant chunks using vector similarity search
def retrieve(state: RAGState) -> dict:
    # Graph node: find the most relevant chunks for the user's question
    documents = vector_store.similarity_search(
        state["question"],   # the user's question from graph state
        k=3,                 # return top-3 most similar chunks
    )
Narration

It gets the current state and returns a dictionary with only the updates, not the whole state.

Remember that every node should get the state as an argument to update it with the new values after the work is done.

Line by line
  • similarity_search is used to find the most relevant chunks for the user's question The question from user's input becomes a vector, and Chroma finds the three nearest chunks by meaning. the k value is used to specify how many chunks to return. More chunks means wider context, but also more noise for llm model. 
  • # 6–7. Retrieve relevant chunks using vector similarity search

# Join the retrieved chunks into one context string for the LLM
context = "\n\n".join(
    document.page_content for document in documents
)
  • When chunks are retrieved, we need to join them into one context string for the LLM. 
  • # Collect unique source URLs (set -> deduplication -> list) to avoid duplicates
sources = list({
    document.metadata["source"]
    for document in documents
})

# Return only the updated state keys (LangGraph merges them)

    "context": context,
    "sources": sources,

  • and finally LangGraph merges these updated keys into the shared state.

Lesson 1. Three streaming modes: values, updates, messages

Goal

0. Lesson intro

Narration

When we call invoke(), we get the final result after the graph has completed. Streaming lets us observe what happens along the way. A node may retrieve documents, another node may update the state, and the language model may generate its answer in small chunks. LangGraph gives us different views of that execution. We'll run our existing RAG graph three times and change only the stream_mode argument. By the end, you'll know which mode to choose for debugging, logging, and displaying generated text.

2. Mode values

Mode

stream_mode="values"

On screen

Add a temporary helper to main.py. We do not need a separate inspect_stream.py file.

python 
async def inspect_values(question: str) -> None:
    state = {
        "question": question,
        "context": "",
        "sources": [],
        "answer": "",
    }

    async for chunk in rag_graph.astream(
        state,
        stream_mode="values",
    ):
        print(chunk)
        print("-" * 60)
Narration

The values mode yields the full graph state after graph steps. Think of each chunk as a snapshot of the agent's working memory. After retrieval, the state can contain the retrieved context and sources. After generation, it can also contain the answer. This mode is especially useful when you want to understand how data moves through the graph. The exact number and timing of snapshots depend on the graph execution; do not assume that an initial empty state is always emitted.

4. Mode messages

Mode

stream_mode="messages"

On screen

async def inspect_messages(question: str) -> None:
    state = {
        "question": question,
        "context": "",
        "sources": [],
        "answer": "",
    }

    async for message_chunk, metadata in rag_graph.astream(
        state,
        stream_mode="messages",
    ):
        print(
            repr(message_chunk.content),
            "| node =",
            metadata.get("langgraph_node"),
        )
text 
'The' | node = generate
' promo' | node = generate
' code' | node = generate
' is' | node = generate
Narration

This is the mode we need when we want to display generated text as it arrives. Each item is a pair: the message chunk and its metadata. The metadata includes langgraph_node, which tells us which graph node produced the chunk. We can use that field to keep only the output from generate. Remember the difference: messages gives us model message chunks, not the full graph state or a list of retrieved sources.

5. Comparison and homework

updates Node-level state updates Logging and collecting node results

The takeaway is straightforward. Choose values when you need to inspect the full state, updates when you need to know what each node changed, and messages when you want to display model output progressively. 2. Write the streaming helper

On screen

Add this helper to the existing main.py. It subscribes to messages and updates in one graph run.

python 
async def ask_question_stream(question: str) -> tuple[str, list[str]]:
    state = {
        "question": question,
        "context": "",
        "sources": [],
        "answer": "",
    }

    answer_parts: list[str] = []
    sources: list[str] = []

    async for mode, payload in rag_graph.astream(
        state,
        stream_mode=["messages", "updates"],
    ):
        if mode == "updates":
            retrieve_update = payload.get("retrieve", {})
            if retrieve_update:
                sources = retrieve_update.get("sources", sources)

        elif mode == "messages":
            message_chunk, metadata = payload

            if metadata.get("langgraph_node") != "generate":
                continue

            content = message_chunk.content
            if isinstance(content, str) and content:
                print(content, end="", flush=True)
                answer_parts.append(content)

    print()
    return "".join(answer_parts), sources
Narration

Because we requested multiple modes, each item from the stream includes the mode name and that mode's payload. When the mode is updates, we look for the result from retrieve and save its sources. When the mode is messages, the payload is the message-chunk and metadata pair we saw in lesson 1. We filter by the generate node, print the text immediately, and append it to a list so we can also return the completed answer. One graph run gives us both the answer and its sources.

Important note

This example assumes the retrieval node returns a field named sources in its update. If your node uses another field name or a different node name, adjust the lookup to match your graph. Also check the multi-mode stream item shape for the LangGraph version used by your project.

Lesson 3. FastAPI + Pydantic wrapper

Goal

Expose the existing RAG application through HTTP with /health, /ask, and /index. Add request validation, configurable retrieval depth, an optional indexing URL, and clear error handling without splitting the lesson across extra files.

0. Lesson intro

Narration

So far, our RAG agent has been used from a Python script. To connect a frontend, mobile application, or another backend, we need an HTTP API. FastAPI gives us routing, request validation, response serialization, and interactive documentation. We'll add it to the same main.py that already contains our RAG logic. The goal is not to build a large production platform; it is to expose the application cleanly and explain the decisions that matter.

1. Install FastAPI

bash 
pip install "fastapi[standard]"
Narration

The standard extra includes Uvicorn, the ASGI server we'll use to run the app. If you're using uv, run uv add "fastapi[standard]". Pydantic is installed as part of the FastAPI dependency stack, so there is no need to install it separately for this example.

2. Define request and response models

On screen

Add these models near the imports in main.py. We will keep the example in one file rather than creating a separate schemas.py.

python 
from pydantic import BaseModel, Field, HttpUrl


class AskRequest(BaseModel):
    question: str = Field(
        min_length=1,
        max_length=2000,
        description="Question for the RAG assistant",
        examples=["What is the promo code?"],
    )
    top_k: int = Field(default=3, ge=1, le=10)


class AskResponse(BaseModel):
    answer: str
    sources: list[str]


class IndexRequest(BaseModel):
    url: HttpUrl | None = Field(
        default=None,
        description="Optional URL. If omitted, SOURCE_URL is used.",
        examples=["https://example.com/"],
    )


class IndexResponse(BaseModel):
    indexed: int
    source: str


class HealthResponse(BaseModel):
    status: str = "ok"
Narration

Pydantic models define the shape of the data entering and leaving the API. AskRequest validates the question and includes top_k, which controls how many documents retrieval should return. The range prevents clients from requesting an unreasonable number of chunks. The IndexRequest model makes the URL optional and validates it as an HTTP URL. When it is omitted, we'll fall back to SOURCE_URL. FastAPI uses these models to validate requests, serialize responses, and generate the API documentation automatically.

3. Pass top_k into retrieval

On screen

Update the existing graph state and retrieval node so the value from the API reaches the vector search. Merge the top_k field into your existing state definition; do not create a second competing state class.

python 
# Add top_k: int to your existing RAG state type.

def retrieve(state: RAGState) -> dict:
    question = state["question"]
    top_k = state.get("top_k", 3)

    docs = vector_store.similarity_search(
        question,
        k=top_k,
    )

    context = "\\n\\n".join(
        doc.page_content for doc in docs
    )

    sources = list(dict.fromkeys(
        doc.metadata.get("source", "")
        for doc in docs
        if doc.metadata.get("source")
    ))

    return {
        "context": context,
        "sources": sources,
    }
Narration

This is the important connection between the API and the RAG pipeline. Adding top_k to the request model alone would not change retrieval. We also pass it into the graph state and read it inside the retrieval node. The default value keeps existing CLI calls working when they do not provide the field. Adapt the vector-store call to the retriever API already used by your project; the key lesson is to pass the parameter all the way through instead of leaving a hard-coded k=3.

4. Make indexing accept an optional URL

Narration

The indexing function should accept a URL but continue to use the configured default when no URL is supplied. It should also return a useful result to the API. Avoid reading private Chroma internals such as _collection.count() just to calculate the number of chunks indexed.

python 
def index_documents(url: str | None = None) -> int:
    target_url = url or SOURCE_URL

    documents = load_data(target_url)
    chunks = text_splitter.split_documents(documents)

    if not chunks:
        return 0

    vector_store.add_documents(chunks)
    return len(chunks)
Important note

This is a structural example: keep the loader, splitter, and vector-store variable names already used in your project. If your current indexing function performs additional steps, keep them. The key change is to accept an optional URL and return the number of chunks added during this call. This count is different from the total number of records already present in the vector database.

Security note

Validating a value as HttpUrl checks its URL structure; it does not make fetching arbitrary URLs safe. Before exposing custom URL indexing publicly, add an SSRF protection policy: restrict allowed hosts, block private and loopback IP ranges after DNS resolution, validate redirects, and set network timeouts. For this lesson, explain the risk rather than turning the course into a full security module.

5. Create the FastAPI app and routes

On screen

Add the FastAPI application below the existing RAG functions in main.py. Keep the route functions synchronous because the graph and indexing calls shown here use synchronous APIs.

python 
from fastapi import FastAPI, HTTPException


app = FastAPI(
    title="RAG Agent API",
    version="1.0.0",
    description="A simple RAG agent exposed over HTTP.",
)


@app.get("/health", response_model=HealthResponse)
def health() -> HealthResponse:
    return HealthResponse(status="ok")


@app.post("/ask", response_model=AskResponse)
def ask(payload: AskRequest) -> AskResponse:
    try:
        result = rag_graph.invoke({
            "question": payload.question,
            "context": "",
            "sources": [],
            "answer": "",
            "top_k": payload.top_k,
        })

        return AskResponse(
            answer=result["answer"],
            sources=result.get("sources", []),
        )
    except Exception as exc:
        raise HTTPException(
            status_code=500,
            detail="The RAG request could not be completed.",
        ) from exc


@app.post("/index", response_model=IndexResponse)
def index(payload: IndexRequest | None = None) -> IndexResponse:
    target_url = str(payload.url) if payload and payload.url else SOURCE_URL

    try:
        indexed_count = index_documents(target_url)
        return IndexResponse(
            indexed=indexed_count,
            source=target_url,
        )
    except Exception as exc:
        raise HTTPException(
            status_code=500,
            detail="Document indexing failed.",
        ) from exc
Narration

We have three routes. /health is a lightweight health check. /ask validates the incoming question, passes both the question and top_k into the graph, and returns the answer with its sources. /index accepts an optional request body: if a URL is provided, it indexes that page; otherwise it uses SOURCE_URL. Notice that the handlers use normal def functions. That is intentional: calling synchronous rag_graph.invoke() or synchronous indexing directly inside an async def handler would block the event loop. If you switch to asynchronous graph or indexing APIs, then an async def route is appropriate.

Error handling

Invalid request data is rejected by FastAPI and Pydantic with HTTP 422 before our route logic runs. Runtime failures are converted to HTTP 500 responses. In a real application, log the exception details on the server and return a safe message to the client; do not expose credentials, stack traces, or internal infrastructure details.

Advanced topic. Streaming to a browser with SSE

Goal

Add a streaming HTTP endpoint that sends generated text to a browser using Server-Sent Events, while keeping the normal /ask endpoint for non-streaming requests.

Narration

We already know how to stream tokens inside Python. Now we need a transport that can carry those chunks over HTTP to a browser. Server-Sent Events, or SSE, is a simple one-way stream from server to client. It fits this use case because the browser sends a question and then listens while the server sends progress and token events. We do not need a bidirectional WebSocket just to deliver generated text.

1. Understand the SSE message format

text 
event: token
data: {"text":"Hello"}

event: sources
data: {"items":["https://example.com/"]}

event: done
data: {"ok":true}
Narration

An SSE frame can contain an event name and a data field. A blank line ends the frame. We'll use named events: token for generated text, sources for retrieved source URLs, done when the response is complete, and error if something fails. Named events make the client code easier to read and avoid inventing a separate end-of-stream marker such as [DONE].

2. Add the SSE endpoint

On screen

Add the endpoint to main.py. This version uses the asynchronous graph stream and yields properly formatted SSE frames.

python 
import asyncio
import json
from fastapi import Request
from fastapi.responses import StreamingResponse


@app.get("/stream")
async def stream_answer(
    request: Request,
    question: str,
    top_k: int = 3,
):
    async def event_generator():
        state = {
            "question": question,
            "context": "",
            "sources": [],
            "answer": "",
            "top_k": top_k,
        }

        try:
            async for mode, payload in rag_graph.astream(
                state,
                stream_mode=["messages", "updates"],
            ):
                if await request.is_disconnected():
                    break

                if mode == "updates":
                    retrieve_update = payload.get("retrieve", {})
                    sources = retrieve_update.get("sources")
                    if sources:
                        yield (
                            "event: sources\\n"
                            f"data: {json.dumps({'items': sources})}\\n\\n"
                        )

                elif mode == "messages":
                    message_chunk, metadata = payload
                    if metadata.get("langgraph_node") != "generate":
                        continue

                    content = message_chunk.content
                    if isinstance(content, str) and content:
                        yield (
                            "event: token\\n"
                            f"data: {json.dumps({'text': content})}\\n\\n"
                        )

            yield "event: done\\ndata: {\\"ok\\": true}\\n\\n"

        except Exception:
            yield (
                "event: error\\n"
                f"data: {json.dumps({'message': 'Generation failed.'})}\\n\\n"
            )

    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",
        },
    )
Narration

The endpoint returns a StreamingResponse with the text/event-stream media type. Inside the generator, we run the graph with both stream modes. Retrieval updates are sent as a sources event, and generated chunks are sent as token events. At the end, we send done. If an exception occurs, we send a safe error event. We also check whether the client has disconnected so we can stop doing unnecessary work.

Important implementation note

The example uses a GET endpoint because the browser's native EventSource API only supports GET and cannot send a JSON request body. For a POST endpoint with a JSON body, use fetch() and read the response with a ReadableStream instead. Also validate question and top_k at the API boundary in a production implementation.

3. Connect from the browser with EventSource

On screen

Create a small HTML page for the demo. It opens the stream and handles each named event.

html 
<input id="question" value="What is the promo code?" />
<button id="start">Ask</button>
<button id="stop">Stop</button>
<pre id="answer"></pre>

<script>
  let source = null;

  document.querySelector("#start").onclick = () => {
    if (source) source.close();

    const question = document.querySelector("#question").value;
    const output = document.querySelector("#answer");
    output.textContent = "";

    const url = new URL("/stream", window.location.origin);
    url.searchParams.set("question", question);

    source = new EventSource(url);

    source.addEventListener("token", (event) => {
      const data = JSON.parse(event.data);
      output.textContent += data.text;
    });

    source.addEventListener("sources", (event) => {
      const data = JSON.parse(event.data);
      output.textContent += "\\n\\nSources:\\n" + data.items.join("\\n");
    });

    source.addEventListener("done", () => {
      source.close();
      source = null;
    });

    source.addEventListener("error", (event) => {
      output.textContent += "\\nStream connection error.";
      if (source) source.close();
      source = null;
    });
  };

  document.querySelector("#stop").onclick = () => {
    if (source) source.close();
    source = null;
  };
</script>
Narration

The browser creates an EventSource and registers handlers for our named events. Each token event appends text to the page. The sources event displays the URLs, and the done event closes the connection. The Stop button calls source.close(), which stops the browser from listening. For a robust production cancellation flow, also ensure the server notices the disconnect and cancels upstream generation where the model and graph APIs support it.

5. Production notes

Notes
  • Proxy buffering: configure reverse proxies such as Nginx not to buffer the SSE response. The X-Accel-Buffering: no header helps with Nginx, but proxy configuration still matters.
  • Timeouts: configure suitable application, load-balancer, and proxy timeouts for long-running streams.
  • Authentication: native EventSource does not provide a general way to attach arbitrary authorization headers. Consider secure same-site cookies or use fetch() with a ReadableStream when custom headers are needed.
  • CORS: configure allowed origins deliberately if the browser client is hosted on a different origin.
  • Validation: validate the question and retrieval parameters, and apply rate limits appropriate to the service.
  • URL indexing: do not expose arbitrary URL fetching publicly without SSRF protections and network restrictions.
  • Observability: log request IDs, duration, model errors, and disconnects without logging secrets or sensitive prompt content unnecessarily.
