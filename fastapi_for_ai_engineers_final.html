Нарратив открытия курса

Представьте, что наш RAG уже работает: он загружает страницу, разбивает её на фрагменты, сохраняет embeddings и отвечает на вопросы. Но пока это инструмент разработчика — запускается из терминала и возвращает ответ только целиком. В этом мини-проекте мы не будем переписывать RAG. Мы добавим ему три способа общения с внешним миром: наблюдение за графом, потоковый вывод в CLI и HTTP API. В финале браузер начнёт получать ответ по частям.

Правило проекта: продолжаем работать в одном файле main.py. Не создаём отдельные schemas.py, server.py и inspect_stream.py. Так ученик видит эволюцию одного приложения, а не тратит время на перемещение кода.
Урок 01 · 20–25 минут

Понимаем streaming в LangGraph

Цель: научиться выбирать правильный режим стриминга, а не просто запомнить названия.

Сценарий / hook

Когда вы вызываете граф обычным invoke(), вы получаете результат в конце. Но во время выполнения внутри графа уже происходят полезные события: retrieval нашёл документы, узел обновил состояние, модель начала генерировать текст. Вопрос не в том, «умеет ли граф стримить», а в том, какие именно события нам нужны.

1. Три режима на одной схеме

valuesПолное состояние графа после выполнения шага
updatesТолько изменения, возвращённые узлом
messagesФрагменты сообщений модели + metadata

Покажите одну и ту же RAG-сессию тремя способами. Важно: values не следует описывать как обязательную выдачу первоначального пустого state. Он показывает состояние после шагов графа.

2. Добавляем инспектор прямо в main.py

В конец существующего main.py временно добавьте функцию ниже. Она не требует нового файла и позволяет переключать режим одной переменной.

Python · демонстрация урока 1
import asyncio

async def inspect_stream(question: str, mode: str = "updates") -> None:
    initial_state = {
        "question": question,
        "context": "",
        "sources": [],
        "answer": "",
    }

    async for event in rag_graph.astream(
        initial_state,
        stream_mode=mode,
    ):
        print(f"\\n--- {mode} ---")
        print(event)

Нарратив / values

Начнём с values. Представьте это как снимок всей рабочей памяти агента после очередного шага: вопрос, контекст, sources и, когда генерация завершится, ответ. Такой режим удобен, когда мы хотим понять, как меняется состояние целиком.

Нарратив / updates

Теперь updates. Это уже не полный снимок, а квитанция о том, что изменил конкретный узел. Для RAG это особенно удобно: мы можем увидеть, что именно вернул retrieve, а затем отдельно — что добавил generate. Меньше шума, если нас интересуют изменения.

Нарратив / messages

И наконец messages. Здесь мы получаем кусочки сообщений модели вместе с метаданными. В метаданных есть langgraph_node, поэтому можно отличить текст, произведённый узлом generate, от сообщений других узлов. Именно этот режим поможет показать пользователю ответ по мере генерации.

Python · чтение messages
async def inspect_messages(question: str) -> None:
    state = {
        "question": question,
        "context": "",
        "sources": [],
        "answer": "",
    }
    async for chunk, metadata in rag_graph.astream(
        state,
        stream_mode="messages",
    ):
        if chunk.content:
            print(
                repr(chunk.content),
                "| node =",
                metadata.get("langgraph_node"),
            )
Точность терминов. В LangGraph есть и другие режимы, включая custom и debug. В этом уроке фокусируемся на трёх наиболее полезных для нашего RAG-приложения. Это учебный выбор, а не полный список возможностей.

Урок 02 · 25–30 минут

Потоковый ответ RAG в CLI

Цель: сделать асинхронную функцию, которая печатает токены по мере поступления и собирает sources в том же запуске графа.

Сценарий / hook

Сравним два пользовательских опыта. В первом человек нажимает Enter и несколько секунд смотрит на пустой терминал. Во втором сразу появляется текст: «The promo code…». Полное время генерации может быть тем же, но воспринимаемая задержка ниже — пользователь видит, что система работает.

1. Проверьте поддержку streaming на стороне модели

2. Собираем токены и sources за один проход

LangGraph позволяет запросить несколько режимов одновременно. При stream_mode=["messages", "updates"] событие содержит имя режима и соответствующую полезную нагрузку. Ниже используем этот формат явно.

Python · streaming helper
async def ask_question_stream(question: str) -> tuple[str, list[str]]:
    state = {
        "question": question,
        "context": "",
        "sources": [],
        "answer": "",
    }
    answer_parts: list[str] = []
    sources: list[str] = []

    async for mode, payload in rag_graph.astream(
        state,
        stream_mode=["messages", "updates"],
    ):
        if mode == "updates":
            retrieve_update = payload.get("retrieve", {})
            if retrieve_update:
                sources = retrieve_update.get("sources", sources)

        elif mode == "messages":
            message_chunk, metadata = payload
            if metadata.get("langgraph_node") != "generate":
                continue

            content = message_chunk.content
            if isinstance(content, str) and content:
                print(content, end="", flush=True)
                answer_parts.append(content)

    print()
    return "".join(answer_parts), sources
Формат события зависит от версии. Для нескольких stream modes LangGraph возвращает пары (mode, chunk). Для одного режима messages обычно приходит пара (message_chunk, metadata). Не смешивайте эти два формата в одном цикле без проверки структуры.
Нарратив / разбор

Смотрите, мы не вызываем retrieve отдельно после генерации. Когда приходит событие updates, забираем список источников из результата узла retrieve. Когда приходит messages, проверяем имя узла и печатаем только фрагменты от generate. Один запуск графа — и для текста, и для sources. Это и быстрее, и логически чище.

Та же функция позже будет полезна для HTTP streaming, хотя в endpoint мы будем отдавать события браузеру, а не печатать их в терминал.

4. Измеряем не только общее время

Для более инженерной подачи введите два понятия: TTFT (time to first token) и полное время ответа. Это помогает объяснить, почему streaming улучшает UX, даже если общая генерация не стала быстрее.

Python · простая телеметрия
import time

async def timed_stream(question: str) -> None:
    started = time.perf_counter()
    first_token_at = None

    state = {
        "question": question,
        "context": "",
        "sources": [],
        "answer": "",
    }

    async for chunk, metadata in rag_graph.astream(
        state,
        stream_mode="messages",
    ):
        if metadata.get("langgraph_node") != "generate":
            continue
        if not chunk.content:
            continue

        if first_token_at is None:
            first_token_at = time.perf_counter()
            print(f"\\nTTFT: {first_token_at - started:.2f}s")

        print(chunk.content, end="", flush=True)

    print(f"\\nTotal: {time.perf_counter() - started:.2f}s")
Примечание к демо: этот короткий таймер показывает TTFT от старта графа, то есть включает retrieval. Это полезная end-to-end метрика для пользователя. Если нужно измерять только задержку модели, поставьте отдельные отметки до и после retrieval.

Нарратив / объяснение

Заодно FastAPI использует эти модели для документации в Swagger UI.

3. Делаем параметры RAG явными

Чтобы top_k из API действительно влиял на поиск, обновите функцию retrieval и узел графа. Не оставляйте число 3 жёстко зашитым внутри.

Python · retrieval
def retrieve(state: RAGState) -> dict:
    question = state["question"]
    top_k = state.get("top_k", 3)

    docs = vector_store.similarity_search(question, k=top_k)
    context = "\\n\\n".join(doc.page_content for doc in docs)
    sources = list(dict.fromkeys(
        doc.metadata.get("source", "")
        for doc in docs
        if doc.metadata.get("source")
    ))

    return {"context": context, "sources": sources}

Добавьте поле в ваш TypedDict state:

При вызове графа передавайте top_k. Если в текущей версии графа тип состояния объявлен иначе, добавьте поле в существующий TypedDict, не создавая второй тип.

4. FastAPI routes — в том же файле

Python · приложение и endpoints
app = FastAPI(
    title="RAG Agent API",
    version="1.0.0",
    description="A RAG assistant exposed over HTTP",
)


@app.get("/health", response_model=HealthResponse)
def health() -> HealthResponse:
    return HealthResponse()


@app.post("/ask", response_model=AskResponse)
def ask(payload: AskRequest) -> AskResponse:
    try:
        result = rag_graph.invoke({
            "question": payload.question,
            "context": "",
            "sources": [],
            "answer": "",
            "top_k": payload.top_k,
        })
    except Exception as exc:
        # В production логируйте подробности на сервере,
        # но не возвращайте внутренний traceback клиенту.
        raise HTTPException(
            status_code=500,
            detail="RAG request failed",
        ) from exc

    return AskResponse(
        answer=result["answer"],
        sources=result.get("sources", []),
    )


@app.post("/index", response_model=IndexResponse)
def index(payload: IndexRequest | None = None) -> IndexResponse:
    target_url = str(payload.url) if payload and payload.url else SOURCE_URL
    try:
        indexed_count = index_documents(target_url)
    except Exception as exc:
        raise HTTPException(
            status_code=500,
            detail="Indexing failed",
        ) from exc

    return IndexResponse(
        indexed=indexed_count,
        source=target_url,
    )
Нарратив / почему def

Обратите внимание: здесь обычные def, а не async def. Наши вызовы rag_graph.invoke() и index_documents() синхронные и могут блокировать выполнение. FastAPI запускает обычные path operation функции в threadpool, поэтому мы не блокируем event loop. Альтернатива — полностью асинхронный путь с await rag_graph.ainvoke() и async-совместимой индексацией. Не стоит писать async def вокруг синхронной тяжёлой функции только ради модного слова async.

URL из запроса — не безобидный параметр. В учебном примере мы принимаем HttpUrl. В публичном production API нужно дополнительно защищаться от SSRF: запрещать localhost, private/link-local IP, внутренние домены и опасные редиректы; ограничивать размер ответа, timeout и допустимые схемы. Проверка Pydantic подтверждает формат URL, но не безопасность адреса.

5. Индексация возвращает точное число новых chunks

Обновите вашу существующую функцию индексации: она должна возвращать число обработанных chunks. Не обращайтесь к приватному vector_store._collection.count() — это внутренний API Chroma и общее число записей в коллекции не обязательно равно числу chunks этой операции.

Python · сигнатура index_documents
def index_documents(url: str | None = None) -> int:
    target_url = url or SOURCE_URL
    documents = load_data(target_url)
    chunks = text_splitter.split_documents(documents)

    if not chunks:
        return 0

    vector_store.add_documents(chunks)
    return len(chunks)

Этот пример предполагает, что load_data уже возвращает LangChain Documents, а text_splitter и vector_store созданы в вашем исходном проекте. Сохраните ваш текущий способ формирования стабильных ID, если он уже реализован: иначе повторная индексация может создавать дубликаты.

Бонус · 25–30 минут

Real-time streaming через Server-Sent Events

Цель: передавать события генерации в браузер через HTTP, не меняя RAG pipeline.

Сценарий / hook

В предыдущем уроке фронтенд получил JSON, когда ответ был готов. А теперь представьте чат-интерфейс: пользователь отправил вопрос, и текст начинает появляться в окне почти сразу. Мы не будем подключать WebSocket ради одного направления данных. Здесь достаточно стандартного HTTP streaming с форматом Server-Sent Events.

1. SSE, JSON и WebSocket — не одно и то же

ПодходМодель обменаКогда подходит
Обычный JSONОдин запрос → один готовый ответПростые API, когда ждать завершения нормально
SSEСервер → клиент, поток событий поверх HTTPТокены, прогресс, уведомления
WebSocketДвунаправленный постоянный каналИнтерактивная связь в обе стороны, realtime-сессии

SSE — текстовый формат. Каждое событие отделяется пустой строкой. Поле data: содержит payload; необязательное event: задаёт тип события.

Text · пример SSE wire format
event: token
data: {"token":"Hello"}

event: token
data: {"token":" there"}

event: sources
data: {"items":["https://example.com/"]}

event: done
data: {}

Реализуем endpoint. Как и в CLI, получаем одновременно messages и updates, чтобы не запускать retrieval второй раз.

class StreamRequest(BaseModel):
    question: str = Field(min_length=1, max_length=2000)
    top_k: int = Field(default=3, ge=1, le=10)


def sse_event(event: str, data: dict) -> str:
    payload = json.dumps(data, ensure_ascii=False)
    return f"event: {event}\\ndata: {payload}\\n\\n"


@app.post("/stream")
async def stream_answer(payload: StreamRequest, request: Request):
    async def event_generator():
        sources: list[str] = []
        try:
            state = {
                "question": payload.question,
                "context": "",
                "sources": [],
                "answer": "",
                "top_k": payload.top_k,
            }

            async for mode, chunk in rag_graph.astream(
                state,
                stream_mode=["messages", "updates"],
            ):
                if await request.is_disconnected():
                    break

                if mode == "updates":
                    retrieve_update = chunk.get("retrieve", {})
                    if retrieve_update:
                        sources = retrieve_update.get("sources", sources)
                        yield sse_event(
                            "sources",
                            {"items": sources},
                        )

                elif mode == "messages":
                    message_chunk, metadata = chunk
                    if metadata.get("langgraph_node") != "generate":
                        continue

                    content = message_chunk.content
                    if isinstance(content, str) and content:
                        yield sse_event("token", {"token": content})

            yield sse_event("done", {})
        except Exception:
            # Подробности — в server logs, клиенту только безопасное сообщение.
            yield sse_event("error", {"message": "Generation failed"})

    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",
        },
    )
Нарратив / построчно

Важная часть здесь — не сам StreamingResponse, а генератор событий внутри него. Он запускает граф и по мере поступления событий выдаёт SSE-строки. События token несут кусочки ответа, sources — найденные ссылки, done — штатное завершение, error — безопасное сообщение об ошибке. Мы также проверяем отключение клиента, чтобы не продолжать ненужную работу, когда браузер закрыл соединение.

Метод и формат клиента. В примере /stream — POST с JSON body. Нативный браузерный EventSource умеет только GET и не позволяет задать произвольное тело запроса. Поэтому для этого endpoint используем fetch() + чтение ReadableStream. Альтернатива — сделать GET endpoint с query-параметрами, если вопрос короткий и допустим в URL.

4. Простой браузерный клиент на fetch + ReadableStream

Это учебный фрагмент для страницы с элементами #question, #send, #answer и #sources. Для production лучше использовать полноценный SSE parser, потому что границы сетевых чанков не обязаны совпадать с границами событий.

JavaScript · браузерный клиент
const answerEl = document.querySelector("#answer");
const sourcesEl = document.querySelector("#sources");

async function askWithStream(question) {
  answerEl.textContent = "";
  sourcesEl.textContent = "";

  const response = await fetch("http://127.0.0.1:8000/stream", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ question, top_k: 3 }),
  });

  if (!response.ok || !response.body) {
    throw new Error(`HTTP ${response.status}`);
  }

  const reader = response.body
    .pipeThrough(new TextDecoderStream())
    .getReader();

  let buffer = "";

  while (true) {
    const { value, done } = await reader.read();
    if (done) break;

    buffer += value;
    const events = buffer.split("\\n\\n");
    buffer = events.pop() ?? "";

    for (const rawEvent of events) {
      const eventName = rawEvent.match(/^event: (.+)$/m)?.[1];
      const dataLine = rawEvent.match(/^data: (.+)$/m)?.[1];
      if (!eventName || !dataLine) continue;

      const data = JSON.parse(dataLine);

      if (eventName === "token") {
        answerEl.textContent += data.token;
      } else if (eventName === "sources") {
        sourcesEl.textContent = data.items.join("\\n");
      } else if (eventName === "error") {
        throw new Error(data.message);
      } else if (eventName === "done") {
        console.log("Stream completed");
      }
    }
  }
}
Нарратив / демонстрация

Покажите сначала curl: видно, что сервер отправляет отдельные события. Затем покажите браузер: текст накапливается в элементе ответа, а ссылки появляются отдельным событием. Подчеркните, что это не WebSocket и не магия фронтенд-фреймворка — это обычный HTTP response, который сервер не закрывает сразу, а постепенно дописывает.

5. Production notes — коротко, без ухода в отдельный курс

  • Disconnect: прекращайте генерацию, если клиент отключился; проверьте, как конкретная версия LangGraph/backend отменяет задачу.
  • Proxy buffering: reverse proxy может буферизовать ответ; настройте его для SSE. Заголовок X-Accel-Buffering: no помогает в окружениях с Nginx.
  • Timeouts: согласуйте таймауты приложения, прокси и клиента.
  • Errors: после начала streaming HTTP status уже нельзя надёжно изменить; отправляйте отдельное SSE-событие error.
  • Auth/CORS: настройте их, если frontend и API находятся на разных origin.
  • EventSource: автоматически переподключается, но это поведение не появляется автоматически при использовании fetch; fetch-клиент должен сам решать, нужен ли retry.
Финальное завершение курса

Мы прошли путь от локального RAG-скрипта до HTTP API с потоковой генерацией. Главное инженерное решение — разделять уровни: LangGraph сообщает о событиях выполнения, FastAPI определяет HTTP-контракт, а SSE доставляет события браузеру. Теперь у вас не просто чат-скрипт, а базовый backend, который можно подключить к интерфейсу.

Бонусное задание: добавьте кнопку Stop, которая отменяет fetch-запрос через AbortController, и покажите пользователю отдельное состояние «соединение прервано».

Сборка проекта

Как должен выглядеть итоговый main.py

Курс развивает исходный файл постепенно. Чтобы ученику было легко ориентироваться, держите в нём логические секции в таком порядке:

  1. Imports и configuration — dotenv, env vars, клиенты модели и embeddings.
  2. Loading and chunking — загрузка страницы, очистка HTML, text splitter.
  3. Vector store — Chroma и функция index_documents(url) -> int.
  4. RAG state and nodes — TypedDict, retrieve, generate.
  5. Graph construction — сборка и компиляция rag_graph.
  6. CLI helpers — обычный ответ и streaming CLI (оставить один выбранный интерфейс запуска).
  7. Pydantic models — request/response схемы.
  8. FastAPI app and routes — /health, /ask, /index.
  9. SSE — sse_event и /stream.
  10. Entry point — запуск CLI или сервера в зависимости от выбранного режима.
Важное замечание о запуске. Для команды uvicorn main:app модуль main.py импортируется как приложение. Не запускайте CLI-интерактивный код безусловно при импорте. Поместите его под if __name__ == "__main__":, а сервер запускайте командой Uvicorn. Не вызывайте uvicorn.run() при каждом импорте модуля.

Что намеренно оставлено за рамками

Авторизация, полноценная dependency injection, Docker, Redis, Postgres, фоновые очереди, multi-tenant isolation и production-grade SSRF resolver — важные темы, но они размоют фокус этого курса. Их лучше вынести в отдельный курс по production deployment.

Рекомендуемый финальный акцент: «Streaming — это не один флаг. Это цепочка: модель должна выдавать chunks → LangGraph должен отдавать нужные события → API должен передать их без буферизации → клиент должен правильно разобрать поток».
