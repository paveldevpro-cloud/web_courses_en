Building a RAG Pipeline

Подробный сценарий видеоурока: от загрузки данных из URL до ответа локальной LLM. Python, LangChain, LangGraph, ChromaDB и Ollama — без FastAPI на первом этапе.

Содержание урока

0. Архитектура урока Часть 1. Индексация 1. Загрузка URL 2. Chunking 3. Embeddings 4. ChromaDB Часть 2. Поиск и генерация 5. User query 6. Retrieval 7. Prompt 8. LangGraph 9. LLM answer 10. Тестирование 11. Итоги Платный Advanced

Цель урока: собрать локальный RAG-прототип, который загружает веб-страницу, индексирует её содержимое, ищет релевантные фрагменты и передаёт их LLM для ответа на вопрос.

Сценарий для видео

Текст ведущего «В этом уроке мы не будем просто отправлять вопрос языковой модели. Мы построим RAG-систему — подход, при котором модель получает дополнительные данные из внешнего источника непосредственно перед генерацией ответа. Это полезно, когда нужно отвечать по документации, внутренним знаниям компании или конкретным файлам, которые не входят в знания модели. У RAG есть два логических процесса. Первый — индексация: мы загружаем документ, разбиваем его на части, превращаем части в векторы и сохраняем их. Второй — обработка вопроса: находим подходящие части, передаём их в контекст модели и получаем ответ. Сегодня реализуем оба процесса, а позже сможем обернуть логику в FastAPI».
URL→Clean text→Chunks→Embeddings→ChromaDB
User question→Retrieval→Context + prompt→LLM→Answer
Важное уточнение: LangChain предоставляет компоненты для работы с документами, embeddings, поиском и моделями. LangGraph управляет потоком выполнения и состоянием между узлами. Для простого линейного сценария LangGraph не обязателен, но он полезен, чтобы показать архитектуру будущих агентных workflows.

Часть 1Индексация документов — Indexing Pipeline

В этой части готовим данные для поиска. На выходе получаем набор текстовых фрагментов, связанных с их векторными представлениями.

1

Get data from URL

Загрузка и извлечение текста из веб-страницы

Темы теории

Что такое RAG и зачем он нуженRAG расшифровывается как Retrieval-Augmented Generation — генерация ответа с использованием извлечённой информации. Вместо надежды только на знания модели мы сначала находим релевантные данные, а затем передаём их модели.
Почему LLM не знает произвольный документМодель не получает автоматически доступ к любой веб-странице или базе компании. Если информация отсутствует в контексте запроса и модельных знаниях, она может ответить неточно или выдумать детали. RAG позволяет добавлять актуальный или частный контекст во время запроса.
Что такое ingestion pipelineЭто процесс поступления и подготовки данных для дальнейшего поиска. В простом примере он начинается с URL, но в реальном приложении источниками могут быть PDF, DOCX, HTML, базы данных и корпоративные хранилища.
HTTP, HTML и извлечение текстаHTTP-клиент получает содержимое страницы, а HTML-парсер извлекает читаемый текст и убирает ненужные элементы вроде скриптов и навигации. Не каждая страница подходит для такого простого способа: JavaScript-страницы и PDF требуют других загрузчиков.
Сценарий для видео «Начинаем с источника данных. Для демонстрации возьмём публичную веб-страницу. Сначала отправим HTTP-запрос, проверим статус ответа и получим HTML. Но HTML содержит не только полезный текст: там есть скрипты, стили, меню и футеры. Поэтому мы извлечём текст и удалим очевидные ненужные элементы. Обратите внимание: на этом шаге мы ещё не используем LLM и не выполняем семантический поиск. Наша задача — получить исходный текст, который можно подготовить для индексации. Для урока достаточно обычной HTML-страницы; в production загрузку документов обычно выносят в отдельный ingestion-процесс».
Практика: реализовать load_data(url) с помощью requests, BeautifulSoup и объекта Document из LangChain. Сохранить URL в metadata как источник.
2

Split data into chunks

Разбиение документа на небольшие фрагменты

Темы теории

Что такое chunkingChunking — разбиение большого документа на более короткие фрагменты. Векторный поиск по небольшим смысловым частям часто точнее, чем поиск по целому длинному документу.
Контекстное окно и лимиты токеновУ моделей есть ограничения на объём входного контекста. Если передать целую большую страницу, в ней может оказаться много ненужного текста, а запрос может превысить лимит или стать дороже.
chunk_size и chunk_overlapchunk_size задаёт желаемый размер фрагмента, а chunk_overlap — сколько текста повторяется между соседними частями. Перекрытие помогает не потерять смысл на границе чанков. В LangChain размер часто задаётся в символах, а не в токенах.
Как размер чанков влияет на поискСлишком маленькие фрагменты могут терять контекст, а слишком большие — содержать много нерелевантной информации. Универсального идеального размера нет: его подбирают под документы и тип вопросов.
Сценарий для видео «Теперь разобьём текст на chunks. Почему не отправить весь документ в embedding-модель и затем в LLM? Потому что поиск должен находить именно тот участок документа, который отвечает на вопрос, а не возвращать целую страницу. Укажем размер фрагмента и небольшое перекрытие. Перекрытие полезно, когда предложение или мысль пересекает границу двух частей. Эти значения — стартовая настройка, а не универсальное правило. В реальном проекте стоит проверить несколько вариантов на типичных вопросах и посмотреть, какие фрагменты извлекаются».
Практика: использовать RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=150) и вывести количество чанков и несколько примеров.
3

Generate embeddings

Преобразование текста в векторные представления

Темы теории

Что такое embeddingsEmbedding — числовой вектор, который представляет текст так, чтобы семантически близкие тексты обычно находились ближе в векторном пространстве. Вектор — это не краткое изложение и не набор ключевых слов, а числовое представление, пригодное для сравнения.
Как модель кодирует семантикуEmbedding-модель преобразует текст в массив чисел фиксированной размерности. По этим числам можно вычислять сходство между запросом и документами. Модель не «понимает» текст как человек, а обучена строить полезные представления для задач сравнения и поиска.
Embedding-модель и LLM — разные компонентыEmbedding-модель используется для поиска, а генеративная LLM — для формирования ответа. Поэтому в проекте могут быть две разные модели с разными задачами и требованиями к ресурсам.
Совместимость embeddingsДокументы и пользовательские запросы должны векторизоваться совместимой моделью и с одинаковыми настройками. Если заменить embedding-модель, обычно требуется заново индексировать документы, иначе векторы могут быть несовместимы по размерности или смыслу.
Сценарий для видео «Следующий этап — embeddings. Компьютеру нужно представить текст в виде чисел, чтобы сравнивать смысл запроса с содержимым документов. Этим занимается embedding-модель. Для локального запуска используем nomic-embed-text через Ollama. Важно не путать её с Llama 3.1, которая будет генерировать ответы. Это разные модели и разные задачи. Также запомните правило: когда мы индексируем документы, а потом ищем по вопросу, оба этапа должны использовать совместимую embedding-модель. Если поменять её позже, потребуется перестроить индекс».
Практика: подключить OpenAIEmbeddings к OpenAI-compatible endpoint Ollama и использовать nomic-embed-text. Проверить, что модель загружена в Ollama.
4

Store embeddings in ChromaDB

Хранение векторов, текстов и метаданных

Темы теории

Что такое vector databaseВекторная база хранит embedding-векторы и позволяет находить близкие к вектору запроса записи. Она часто хранит также исходный текст и metadata, чтобы после поиска можно было вернуть полезные фрагменты.
Векторная БД и SQL-БДSQL-база удобна для транзакций, связей и точных фильтров. Векторная база оптимизирована для поиска по сходству векторов. В production они могут использоваться вместе, а не обязательно заменять друг друга.
Collection, ID и metadataCollection группирует записи, ID помогает идентифицировать и обновлять их, а metadata хранит дополнительные поля: источник, документ, раздел, владельца или категорию. Metadata пригодны для фильтрации и отображения источников.
ChromaDB и QdrantChromaDB удобна для учебного локального прототипа. Qdrant — отдельная векторная БД, которую можно рассмотреть для более сложных сценариев. Миграция между ними требует переноса данных и проверки настроек поиска, а не только смены названия класса.
Сценарий для видео «Теперь нужно сохранить фрагменты так, чтобы мы могли найти их по смыслу позже. ChromaDB будет хранить векторы, текст чанков и метаданные. Мы зададим локальную директорию, поэтому индекс сохранится между запусками программы. URL запишем в metadata — это позволит понимать, откуда пришёл найденный фрагмент. Для учебного проекта используем ChromaDB, потому что её легко запустить локально. В дальнейшем можно изучить Qdrant, но важно понимать: выбор базы — это архитектурное решение, которое зависит от требований к фильтрации, эксплуатации и масштабу».
Практика: сохранить чанки в ChromaDB, задать уникальные ID и проверить количество записей в коллекции.

Часть 2Поиск и генерация — Retrieval & Generation

Теперь индекс готов. На каждый вопрос мы ищем релевантные фрагменты и используем их как контекст для генерации.

5

Receive user query

Получение вопроса пользователя

Темы теории

Что такое queryQuery — запрос, по которому система должна найти полезные фрагменты. Качество формулировки влияет на то, какие части документов будут извлечены.
Запрос и документ выполняют разные ролиДокументы индексируются заранее, а пользовательские запросы поступают во время работы системы. Для обоих создаются embeddings, но один процесс подготавливает индекс, а другой использует его.
Одинаковая embedding-модельВопрос преобразуется той же совместимой embedding-моделью, что использовалась при индексации документов. В LangChain vector store обычно выполняет это автоматически внутри метода поиска.
Почему пока без FastAPIНа первом уроке достаточно обычной функции Python и input(). Это позволяет изучить RAG без одновременного изучения HTTP-эндпоинтов, схем запросов и серверного запуска. Позже эту функцию можно вызвать из FastAPI endpoint.
Сценарий для видео «Индекс подготовлен, теперь переходим к пользовательскому вопросу. Пока не будем добавлять FastAPI: сначала важно понять внутреннюю механику RAG. Получим вопрос через input и передадим его в функцию обработки. В реальном приложении вопрос поступал бы в API endpoint, но сама логика поиска и генерации могла бы остаться отдельной функцией или сервисом. Такое разделение помогает повторно использовать бизнес-логику в CLI, API и тестах».
Практика: реализовать ask_question(question) и проверить, что непустой вопрос передаётся в workflow.
6

Retrieve relevant chunks

Семантический поиск и top-K

Темы теории

Retrieval и semantic searchRetrieval — извлечение из индекса материалов, которые могут помочь ответить на вопрос. Семантический поиск сравнивает вектор вопроса с векторами чанков, а не просто ищет совпадение слов.
Similarity и distance metricsСходство или расстояние позволяют ранжировать результаты. Часто используются cosine similarity, dot product или евклидово расстояние. Интерпретация чисел зависит от выбранной метрики и реализации, поэтому не следует считать один универсальный порог правильным для всех баз.
Что означает top-KK — количество фрагментов, которые поиск вернёт для дальнейшей обработки. Например, k=3 возвращает три результата. Маленькое K ограничивает контекст, а большое может добавить шум, увеличить задержку и расход токенов.
Похожий фрагмент не всегда правильныйПоиск ранжирует текст по близости к запросу, но не гарантирует, что найденные фрагменты содержат ответ. Поэтому нужно проверять результаты и отдельно оценивать качество retrieval.
Сценарий для видео «Теперь находим три наиболее близких фрагмента. Вызов similarity_search принимает вопрос, преобразует его в embedding и выполняет поиск по ChromaDB. Это скрывает несколько технических шагов за одним удобным методом. Но обратите внимание: top-3 — просто параметр нашего примера, а не оптимальное значение для любой системы. Давайте выведем найденные фрагменты на экран до вызова LLM. Так мы сможем понять, нашёл ли поиск нужную информацию. Если retrieval ошибся, генеративная модель может не суметь исправить эту проблему».
Практика: вызвать similarity_search(question, k=3), вывести тексты результатов, их metadata и источники.
7

Build the prompt with retrieved context

Передача контекста языковой модели

Темы теории

Что такое prompt engineering в RAGPrompt — инструкция и данные, которые мы передаём модели. В RAG prompt объединяет найденный контекст и вопрос, чтобы модель могла сформировать ответ с опорой на документы.
System message и user messageSystem message задаёт общие правила ответа, например использовать только предоставленный контекст. User message содержит конкретный вопрос. Такое разделение делает назначение каждой части prompt более понятным.
Переменные context и questionВ prompt template передаются текст найденных чанков и вопрос пользователя. Если контекст пустой или нерелевантный, модель не получает надёжной основы для ответа — это нужно учитывать в логике приложения.
Prompt injection и недоверенные документыСодержимое документа может включать текст, похожий на инструкции модели. Поэтому prompt должен ясно трактовать найденные документы как данные, а не как источник управляющих инструкций. Одной формулировки prompt недостаточно для полноценной защиты.
Сценарий для видео «У нас есть вопрос и найденные фрагменты. Теперь объединим их в prompt. В system message попросим модель отвечать на основе предоставленного контекста и честно говорить, если информации недостаточно. Сам вопрос передадим отдельным human message. Это важный этап: мы не просто отправляем вопрос модели, а добавляем к нему результаты retrieval. При этом документы считаются недоверенными данными. Инструкции внутри документа не должны менять правила работы системы. В реальном приложении безопасность дополнительно обеспечивается кодом, проверками и контролем доступа».
Практика: создать ChatPromptTemplate с переменными {context} и {question}, затем проверить сформированные сообщения перед вызовом модели.
8

Build the workflow with LangGraph

Оркестрация этапов через state, nodes и edges

Темы теории

Зачем LangGraph, если есть LangChainLangChain предоставляет компоненты и интеграции для моделей, промптов, документов и поиска. LangGraph позволяет описывать процесс как граф узлов с общим состоянием, переходами и, при необходимости, ветвлениями и циклами.
StateState — данные, которые workflow использует и передаёт между этапами. В нашем примере состояние содержит вопрос, контекст, список источников и ответ.
Nodes и edgesNode выполняет отдельную задачу, например поиск фрагментов или генерацию ответа. Edge задаёт переход между узлами. Так логика разделяется на понятные этапы.
Когда нужен графДля простой последовательности можно обойтись обычными функциями или цепочкой. LangGraph особенно полезен, когда появляются условные переходы, повторные попытки, инструменты, human-in-the-loop или более сложный агентный workflow.
Сценарий для видео «Мы могли бы вызвать retrieval и генерацию последовательно прямо внутри одной функции. Но для знакомства с LangGraph представим наш процесс в виде графа. Создадим state, который будет хранить вопрос, контекст, источники и итоговый ответ. Первый узел извлекает фрагменты, второй вызывает LLM. Рёбра задают порядок выполнения: сначала retrieve, затем generate. Сейчас граф линейный, но его можно расширить: например, добавить проверку качества контекста и повторный поиск, если результатов недостаточно. Для такого простого RAG LangGraph — учебный архитектурный выбор, а не обязательное требование».
Практика: описать TypedDict для состояния, зарегистрировать узлы в StateGraph, задать переходы, вызвать compile().
9

Invoke the LLM and return the answer

Генерация ответа на основе найденного контекста

Темы теории

Как LLM использует контекстМодель получает prompt с вопросом и извлечёнными фрагментами. Она формирует ответ на основе доступного контекста и своих обученных параметров; RAG не означает, что модель переобучается на каждом документе.
Hallucinations и ограничения RAGRAG снижает необходимость полагаться только на память модели, но не гарантирует истинность ответа. Ошибки могут возникнуть из-за плохих документов, неудачного поиска, неоднозначного prompt или самой модели.
Если ответ не найденНужно предусмотреть сценарий, в котором контекст пустой или не содержит ответа. Можно вернуть сообщение о недостатке данных, не вызывать LLM в очевидно пустом случае или применять дополнительные проверки релевантности.
invoke и streaminvoke() обычно возвращает результат после завершения вызова. Потоковая генерация позволяет получать части ответа по мере их появления, что полезно для интерфейсов с быстрым отображением текста. Streaming не заменяет retrieval — это способ выдачи результата.
Сценарий для видео «На последнем этапе workflow формирует сообщения и вызывает языковую модель. Для локальной генерации используем Llama 3.1 через Ollama. После завершения вызова извлекаем текст ответа и показываем пользователю. Важно понимать, что наличие контекста не гарантирует правильный ответ. Если поиск вернул не те фрагменты, модель может ответить неверно. Поэтому в следующем этапе мы проверим не только текст ответа, но и источники, которые попали в контекст. В более продвинутой версии можно добавить потоковую выдачу, оценку релевантности и обработку отказов».
Практика: вызвать llm.invoke(messages), сохранить результат в поле answer состояния и вывести его в консоль.

Проверка10. Test and debug the RAG pipeline

Проверка индексаУбедитесь, что чанки действительно записаны в ChromaDB и остаются доступными после перезапуска. При повторной индексации одного URL продумайте, как избежать дубликатов и как удалять устаревшие фрагменты.
Проверка retrieval отдельно от LLMСначала смотрите на найденные чанки. Если они не отвечают на вопрос, проблема может быть в данных, chunking, embedding-модели или параметрах поиска, а не в генеративной модели.
Проверка ответаЗадайте вопросы, на которые ответ точно есть в документе, вопросы с косвенной формулировкой и вопросы, ответа на которые в документе нет. Сравните ответы и посмотрите, признаёт ли модель нехватку информации.
Диагностика окруженияПроверьте, что Ollama запущена, модели загружены, API endpoint доступен, а embedding-модель используется одинаково при индексации и поиске. Не помещайте реальные секреты в код или публичный репозиторий.
Сценарий для видео «Перед тем как считать проект готовым, проверим его по частям. Сначала посмотрим, сколько чанков хранится в базе. Затем выведем результаты поиска и убедимся, что среди них есть нужная информация. Только после этого оценим финальный ответ. Я рекомендую протестировать минимум три сценария: вопрос с прямым ответом в документе, вопрос, требующий объединить информацию, и вопрос, ответа на который нет. Такой тест показывает, что RAG — это не только вызов модели: качество зависит от всего пути данных».
Практика: подготовить 3–5 контрольных вопросов, распечатать retrieval results и сравнить ответы с ожидаемым содержимым документа.

Завершение11. Review architecture and next steps

Сценарий для видео

Текст ведущего «Давайте подведём итог. Сначала мы загрузили документ, очистили его текст и разбили на чанки. Затем создали embeddings и сохранили их вместе с текстом и metadata в ChromaDB. Когда пользователь задаёт вопрос, система выполняет поиск релевантных фрагментов, собирает prompt, вызывает LLM и возвращает ответ. Это базовый RAG pipeline, но пока ещё учебный прототип. Здесь нет API-слоя, авторизации, фоновой обработки больших документов, мониторинга и систематической оценки качества. В следующем этапе мы можем обернуть логику в FastAPI, добавить ACL, улучшить retrieval, автоматизировать ingestion и научиться измерять качество ответов».
