Block 2. Rag pipeline logic

Narration

Before we write code, let’s get the logic. RAG means Retrieval-Augmented Generation. It works in two phases. Indexing and Answering questions. For Indexing: take a document, split it into chunks, turn them into vectors, and put them in a store. To Answera question, find the most similar chunks and give them to the model as context.

Every RAG system starts with data. We’ll download a page, remove the noise — scripts, styles, navigation, and footer — and keep only clean text. The rule I follow is simple: get rid of unnecessary content to reduce hallucinations. The cleaner the data, the more accurate the search.

Block 3. Indexing and getting data from URL

Narration

Let's start with the indexing phase. We need to get data from the URL and split it into chunks. Create a load_data function that will do this for us.

  • First of all, we need to get data from the URL that we passed as an argument, using the requests library.
  • Then we need to parse the HTML content using the BeautifulSoup library.
  • Now we need to remove the noise from the content using the following tags: script, style, nav, footer. Because these tags are not needed for the content and they will only add garbage to the content.
  • Also, let's add validation to the function: if the content is not found, we will raise an error.
  • And the final step — where the magic happens — is to return the chunks as a list of Document objects. For this purpose, we will use the Document class from the LangChain library.
python 
def load_data(url: str) -> list[Document]:
    response = requests.get(
        url,
        timeout=20,
        headers={"User-Agent": "RAG-Tutorial/1.0"},
    )
    response.raise_for_status()

    soup = BeautifulSoup(response.text, "html.parser")

    for tag in soup(["script", "style", "nav", "footer"]):
        tag.decompose()

    text = soup.get_text(separator=" ", strip=True)

    if not text:
        raise ValueError("No text content found at the URL")

    return [Document(page_content=text, metadata={"source": url})]

Block 6. Split data into chunks

Narration

Why not just give the model the whole page? First, models have a limited context window. Second, search over a huge text gets fuzzy. So we split a large document into chunks — small meaning-sized pieces.

when we got our data from the URL, we need to split it into chunks.

python 
# 2. Split data into chunks
def split_documents(documents: list[Document]) -> list[Document]:
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=800,
        chunk_overlap=150,
    )
    return splitter.split_documents(documents)

In the code, we use RecursiveCharacterTextSplitter class from LangChain library. It will split the text into chunks of 800 characters with 150 characters overlap. Why did we choose numbers of characters? Because it is a good balance between the context window of the model and the accuracy of the search. The overlap is important to avoid losing context when the chunks are joined together. You can experiment with different values to find the best one for your model.

Block 7. Vector store and prompt

Narration

when we finished with the splitting, we need to store the chunks in a vector store. We will use Chroma class from LangChain library. It will store the chunks in a vector store. lets create vector store.

python 
vector_store = Chroma(
    collection_name="rag_documents",  # collection name, like a table name in a regular database.
    embedding_function=embeddings,  # tell the store which model to use for vectors
    persist_directory=DB_PATH,  # persist_directory points to the location on the disk.
)

A vector store holds text chunks together with their vectors and can instantly find the nearest ones. embedding_function tell the store which model to use for vectors, both when adding and when searching. It must be the same model, or the "maps of meaning" won't line up. And persist_directory points to the location on the disk where the data will be stored. if the directory does not exist, it will be created.

python 
# 3–4. Generate embeddings and store chunks in ChromaDB
def index_documents() -> None:
    documents = load_data(SOURCE_URL)
    chunks = split_documents(documents)

    # identifiers for each chunk, to avoid duplicates in case of a second run.
    ids = [
        hashlib.sha256(
            f"{chunk.metadata['source']}:{i}:{chunk.page_content}".encode()
        ).hexdigest()
        for i, chunk in enumerate(chunks)
    ]

    vector_store.add_documents(documents=chunks, ids=ids)  # add the chunks to the vector store.

    print(f"Indexed {len(chunks)} chunks from {SOURCE_URL}")

Then we'll build the list of identifiers for each chunk using unique ID based on a hash, to avoid duplicates in case of a second run. And finally we will use add_documents method from Chroma class to add the chunks to the vector store. And print information about the number of chunks that were added.

Block 9. Graph state

Narration

Now one of the most interesting parts. LangGraph describes a process as a graph: nodes are steps, edges are transitions between them. To save the state between the nodes, we will use a dictionary,that every node reads and updates. You can consider it like a memory. We will use TypedDict class from typing module to define the schema of the state.

Block 10. Nodes and the retrieval step

Narration

Now lets create our nodes.retrieve function will create the retrieval node. It performs semantic search to retrieve the most relevant chunks based on vector similarity.

python 
# 6–7. Retrieve relevant chunks using vector similarity search
def retrieve(state: RAGState) -> dict:
    # Graph node: find the most relevant chunks for the user's question
    documents = vector_store.similarity_search(
        state["question"],   # the user's question from graph state
        k=3,                 # return top-3 most similar chunks
    )
Narration

It gets the current state and returns a dictionary with only the updates, not the whole state.

Remember that every node should get the state as an argument to update it with the new values after the work is done.

LangGraph Streaming: Modes & CLI

LangGraph · Ollama · Intermediate. Understand the three streaming modes, inspect graph events, and build a CLI that streams tokens while collecting sources in a single graph run.

Block 0. What we are going to build

Narration

Our RAG application already works: it loads a page, splits it into chunks, stores embeddings, retrieves relevant documents, and generates answers.

But there is one limitation. When we call the graph with invoke(), we receive the final result only after the entire execution is complete. The user has to wait while retrieval and generation happen in the background.

In this lesson, we'll make the application more responsive. First, we'll explore the three main LangGraph streaming modes. Then we'll use them to stream the model's response directly to the terminal while collecting the retrieved sources from the same graph run.

We won't rewrite the RAG pipeline or create another application. We'll build on top of the code you already have in main.py.

Block 1. Why streaming matters

Narration

Before looking at the code, let's understand the user experience we're trying to improve.

The first case: Without streaming. A user enters the question and presses Enter. The terminal remains empty while the application retrieves relevant documents, sends the prompt to the LLM, and waits for the complete response.

After a few seconds, the entire answer appears at once:

During the waiting period, the user receives no visible feedback. The user cannot tell whether the application is processing the request, stuck, or has stopped working.

Let's consider the second case: With streaming. The user enters the same question and presses Enter. This time, the response starts appearing as soon as the model produces its first tokens: "The promo code..."

The rest of the answer gradually appears on the screen. The user can already start reading while the model is still generating the remaining text.

Here's the important distinction: streaming does not necessarily make the model generate the answer faster. The total generation time may remain the same. What changes is the time to first visible output — and therefore the user's perception of latency.

Instead of waiting several seconds without feedback, the user sees that the application is working. The interaction feels more responsive and natural.

That's why streaming matters: it improves the experience of waiting, even when it doesn't reduce the actual processing time.

Block 2. Three streaming modes

Mode What you get When to use it
values Full graph state after a step Inspect the complete state
updates Updates returned by individual nodes Track what each node changes
messages Model message chunks and metadata Stream generated text
Narration

LangGraph provides three main streaming modes. They expose different parts of the graph's execution.

values — the full state. Think of it as a snapshot of the graph's working memory after a step: the question, context, sources, and the answer as it becomes available. It's useful when you want to see how the entire state evolves while the graph runs.

updates — changes made by nodes. Unlike values, this mode doesn't provide a full snapshot of the graph state. Instead, it shows the updates returned by individual nodes. For our RAG pipeline, this lets us inspect what the retrieve node returns and what the generate node adds.

messages — model output as it is generated. This mode streams message chunks together with metadata. It is especially useful for chat interfaces and terminal applications where users should see the answer appear progressively instead of waiting for the complete response.

The key difference is simple: use values to inspect the full state, updates to track node changes, and messages to stream model output.

Block 3. Inspect streaming events in main.py

Narration

Let's see what these modes actually return. We'll start by adding a small inspection function to our existing main.py.

The mode parameter lets us switch between values and updates without changing the rest of the function.

python 
import asyncio

async def inspect_stream(question: str, mode: str = "updates") -> None:
    initial_state = {
        "question": question,
        "context": "",
        "sources": [],
        "answer": "",
    }

    async for event in rag_graph.astream(
        initial_state,
        stream_mode=mode,
    ):
        print(f"\n--- {mode} ---")
        print(event)

Narration · values

Start with values. Each event gives us the graph's current state after a step. You can inspect fields such as question, context, sources, and answer.

This is useful when debugging the pipeline because you can see how the state changes as the graph moves from retrieval to generation.

Narration · updates

Now let's look at updates. Unlike values, it doesn't provide a full snapshot of the graph state. Instead, it shows the changes returned by each node, so you can track what was updated at each step.

For our RAG pipeline, this is particularly useful: we can inspect the output of retrieve and then see what generate adds. There's less noise when we're interested in the work performed by a specific node.

Narration · messages

Finally, let's inspect messages. This mode gives us model message chunks together with metadata.

The metadata includes langgraph_node, which tells us which graph node produced the chunk. We can use this information to keep only the output from our generate node.

This is the mode we'll use to display the answer progressively.

python 
async def inspect_messages(question: str) -> None:
    state = {
        "question": question,
        "context": "",
        "sources": [],
        "answer": "",
    }

    async for chunk, metadata in rag_graph.astream(
        state,
        stream_mode="messages",
    ):
        if chunk.content:
            print(
                repr(chunk.content),
                "| node =",
                metadata.get("langgraph_node"),
            )
Important

Notice that the event structure depends on the streaming mode. With a single messages mode, we receive a (message_chunk, metadata) pair.

With multiple stream modes enabled together, LangGraph returns events in the form of (mode, payload). We'll use that format in the next block.

Block 4. Stream tokens and collect sources in one run

Narration

Now let's combine what we've learned.

Our goal is to stream the answer to the terminal while also collecting the sources returned by the retrieval node.

We could run retrieval separately to get the sources, but that would mean doing the same work twice. Instead, we'll ask LangGraph for two streaming modes in one graph execution: messages and updates.

We'll use messages to receive generated text and updates to capture the sources returned by the retrieve node.

python 
async def ask_question_stream(question: str) -> tuple[str, list[str]]:
    state = {
        "question": question,
        "context": "",
        "sources": [],
        "answer": "",
    }

    answer_parts: list[str] = []
    sources: list[str] = []

    async for mode, payload in rag_graph.astream(
        state,
        stream_mode=["messages", "updates"],
    ):
        if mode == "updates":
            retrieve_update = payload.get("retrieve", {})
            if retrieve_update:
                sources = retrieve_update.get("sources", sources)

        elif mode == "messages":
            message_chunk, metadata = payload

            if metadata.get("langgraph_node") != "generate":
                continue

            content = message_chunk.content

            if isinstance(content, str) and content:
                print(content, end="", flush=True)
                answer_parts.append(content)

    print()
    return "".join(answer_parts), sources
Narration · Walkthrough

Let's walk through the function.

First, we prepare the initial graph state and create two lists: answer_parts for the generated text and sources for the retrieved document references.

Then we call rag_graph.astream() with both streaming modes enabled.

When the event mode is updates, we look for the retrieve node and extract its sources. This assumes that your retrieval node returns a sources field in its state update.

When the event mode is messages, we inspect the metadata and ignore chunks that were not produced by generate. For each text chunk, we print it immediately using flush=True and save it in answer_parts.

At the end, we join the chunks into one complete answer and return it together with the sources.

One graph run gives us both the streamed answer and the source information. No second retrieval call is needed.

Important

This example assumes that your retrieve node returns a field named sources. If your state uses a different field name or your node returns a different structure, adjust the extraction accordingly.

Also, when using multiple stream modes, remember that each event is a (mode, payload) pair. With a single messages mode, the event structure is different.

Block 7. Measure TTFT, not only total time

Narration

We know that streaming makes the application feel more responsive. But how can we measure that improvement?

One useful metric is TTFT, or time to first token. It measures how long the application takes to produce the first visible piece of the model's response.

We should also measure total response time. Comparing these two values helps us understand the difference between starting to receive output earlier and completing the entire response faster.

python 
import time

async def timed_stream(question: str) -> None:
    started = time.perf_counter()
    first_token_at = None

    state = {
        "question": question,
        "context": "",
        "sources": [],
        "answer": "",
    }

    async for chunk, metadata in rag_graph.astream(
        state,
        stream_mode="messages",
    ):
        if metadata.get("langgraph_node") != "generate":
            continue

        if not chunk.content:
            continue

        if first_token_at is None:
            first_token_at = time.perf_counter()
            print(f"\nTTFT: {first_token_at - started:.2f}s")

        print(chunk.content, end="", flush=True)

    print(f"\nTotal: {time.perf_counter() - started:.2f}s")
Note

This example measures TTFT from the beginning of the graph execution, so the value includes retrieval time. That's useful for understanding the end-to-end experience from the user's perspective.

If you want to measure model latency separately, record another timestamp immediately before generation starts.

python 
app = FastAPI(
    title="RAG Agent API",
    version="1.0.0",
    description="A RAG assistant exposed over HTTP",
)


@app.get("/health", response_model=HealthResponse)
def health() -> HealthResponse:
    return HealthResponse()


@app.post("/ask", response_model=AskResponse)
def ask(payload: AskRequest) -> AskResponse:
    try:
        result = rag_graph.invoke({
            "question": payload.question,
            "context": "",
            "sources": [],
            "answer": "",
            "top_k": payload.top_k,
        })
    except Exception as exc:
        # In production log details on the server,
        # but do not return an internal traceback to the client.
        raise HTTPException(
            status_code=500,
            detail="RAG request failed",
        ) from exc

    return AskResponse(
        answer=result["answer"],
        sources=result.get("sources", []),
    )


@app.post("/index", response_model=IndexResponse)
def index(payload: IndexRequest | None = None) -> IndexResponse:
    target_url = str(payload.url) if payload and payload.url else SOURCE_URL
    try:
        indexed_count = index_documents(target_url)
    except Exception as exc:
        raise HTTPException(
            status_code=500,
            detail="Indexing failed",
        ) from exc

    return IndexResponse(
        indexed=indexed_count,
        source=target_url,
    )
Narration · Why def

These are plain def routes, not async def. Our rag_graph.invoke() and index_documents() calls are synchronous and can block. FastAPI runs normal path functions in a threadpool, so we do not block the event loop. The alternative is a fully async path with await rag_graph.ainvoke(). Do not wrap a heavy sync function in async def just to look async.

Warning

A URL from the request is not a harmless parameter. In this teaching example we accept HttpUrl. In a public production API you must also guard against SSRF: block localhost, private IPs, internal hosts, and dangerous redirects; limit response size, timeouts, and schemes. Pydantic checks URL format — not address safety.

Block 6. Indexing returns the chunk count

def index_documents(url: str | None = None) -> int:
    target_url = url or SOURCE_URL
    documents = load_data(target_url)
    chunks = text_splitter.split_documents(documents)

    if not chunks:
        return 0

    vector_store.add_documents(chunks)
    return len(chunks)
Narration

Block 1. Lesson goal

Block 2. SSE vs JSON vs WebSocket

Approach Exchange model When it fits
Plain JSON One request → one finished response Simple APIs where waiting is fine
SSE Server → client event stream over HTTP Tokens, progress, notifications
WebSocket Bidirectional persistent channel Interactive two-way realtime sessions
Narration

SSE is a text format. Events are separated by a blank line. The data: field holds the payload; optional event: sets the event type.

text

Block 3. Add POST /stream

Narration

Add imports, then implement the endpoint. As in the CLI lesson, stream messages and updates together so retrieval does not run twice.

python 
import json
from fastapi import Request
from fastapi.responses import StreamingResponse
python 
class StreamRequest(BaseModel):
    question: str = Field(min_length=1, max_length=2000)
    top_k: int = Field(default=3, ge=1, le=10)


def sse_event(event: str, data: dict) -> str:
    payload = json.dumps(data, ensure_ascii=False)
    return f"event: {event}\ndata: {payload}\n\n"


@app.post("/stream")
async def stream_answer(payload: StreamRequest, request: Request):
    async def event_generator():
        sources: list[str] = []
        try:
            state = {
                "question": payload.question,
                "context": "",
                "sources": [],
                "answer": "",
                "top_k": payload.top_k,
            }

            async for mode, chunk in rag_graph.astream(
                state,
                stream_mode=["messages", "updates"],
            ):
                if await request.is_disconnected():
                    break

                if mode == "updates":
                    retrieve_update = chunk.get("retrieve", {})
                    if retrieve_update:
                        sources = retrieve_update.get("sources", sources)
                        yield sse_event(
                            "sources",
                            {"items": sources},
                        )

                elif mode == "messages":
                    message_chunk, metadata = chunk
                    if metadata.get("langgraph_node") != "generate":
                        continue

                    content = message_chunk.content
                    if isinstance(content, str) and content:
                        yield sse_event("token", {"token": content})

            yield sse_event("done", {})
        except Exception:
            # Details go to server logs; client gets a safe message only.
            yield sse_event("error", {"message": "Generation failed"})

    return StreamingResponse(
        event_generator(),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "X-Accel-Buffering": "no",
        },
    )
Narration · Line by line

The important part is not StreamingResponse itself, but the event generator inside it. It runs the graph and yields SSE strings. token carries answer chunks, sources carries links, done means a clean finish, error is a safe failure message. We also check client disconnect so we stop work when the browser closes the connection.

Warning

In this example /stream is POST with a JSON body. Native browser EventSource only supports GET and cannot set an arbitrary body. Use fetch() + ReadableStream for this endpoint — or expose a GET with query params if the question is short enough for a URL.

Block 5. Browser client with fetch + ReadableStream

Narration

Teaching snippet for a page with #question, #send, #answer, and #sources. In production prefer a real SSE parser — network chunk boundaries need not match event boundaries.

javascript 
const answerEl = document.querySelector("#answer");
const sourcesEl = document.querySelector("#sources");

async function askWithStream(question) {
  answerEl.textContent = "";
  sourcesEl.textContent = "";

  const response = await fetch("http://127.0.0.1:8000/stream", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ question, top_k: 3 }),
  });

  if (!response.ok || !response.body) {
    throw new Error(`HTTP ${response.status}`);
  }

  const reader = response.body
    .pipeThrough(new TextDecoderStream())
    .getReader();

  let buffer = "";

  while (true) {
    const { value, done } = await reader.read();
    if (done) break;

    buffer += value;
    const events = buffer.split("\n\n");
    buffer = events.pop() ?? "";

    for (const rawEvent of events) {
      const eventName = rawEvent.match(/^event: (.+)$/m)?.[1];
      const dataLine = rawEvent.match(/^data: (.+)$/m)?.[1];
      if (!eventName || !dataLine) continue;

      const data = JSON.parse(dataLine);

      if (eventName === "token") {
        answerEl.textContent += data.token;
      } else if (eventName === "sources") {
        sourcesEl.textContent = data.items.join("\n");
      } else if (eventName === "error") {
        throw new Error(data.message);
      } else if (eventName === "done") {
        console.log("Stream completed");
      }
    }
  }
}
Narration · Demo

Show curl first: the server sends separate events. Then show the browser: text accumulates in the answer element, links arrive as their own event. Emphasize: this is not WebSocket and not frontend-framework magic — it is a normal HTTP response the server keeps writing to.

Block 6. Production notes and closing

  • Disconnect: stop generation when the client leaves; check how your LangGraph/backend version cancels the task.
  • Proxy buffering: reverse proxies may buffer; configure them for SSE. X-Accel-Buffering: no helps with Nginx.
  • Timeouts: align app, proxy, and client timeouts.
  • Errors: after streaming starts you cannot reliably change the HTTP status — send an error SSE event.
  • Auth / CORS: configure them if frontend and API are on different origins.
  • EventSource: auto-reconnects, but that does not appear automatically with fetch — the fetch client must decide about retries.
Narration · Course closing

We went from a local RAG script to an HTTP API with streaming generation. The key engineering idea is layering: LangGraph reports execution events, FastAPI defines the HTTP contract, SSE delivers events to the browser. You no longer have only a chat script — you have a basic backend you can attach to a UI.
